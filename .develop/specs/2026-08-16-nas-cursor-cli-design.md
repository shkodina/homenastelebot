# NAS Cursor CLI — design

Дата: 2026-08-16

## Цель

Гибрид в меню Cursor:

- **Use** — как сейчас: облачный агент (`POST /v1/agents`), без shell NAS.
- **NAS** — локальный Cursor CLI (`agent`) **на хосте**, полный shell как у агента в этой IDE (терминал, файлы, docker/`sudo` от пользователя сервиса).

Перед каждым NAS-запросом — кнопка **Выполнить**. Не Python SDK. Не свой MCP под bash.

## Не делаем

- Не заменяем облачный Use.
- Не ставим CLI внутрь контейнера `homenasbot` (там `/host:ro`, нет нормального shell хоста).
- Не пишем MCP «чтобы был shell»: у `agent` shell уже есть.
- Не даём NAS-режим без Telegram-confirm.
- Не коммитим ключи, промпты, пути с секретами.

## UX

```
Cursor
├── Status
├── Use     облако
└── NAS     локальный CLI на хосте
```

Поток NAS:

1. Кнопка **NAS** → «Жду запрос. Следующее сообщение уйдёт локальному Cursor на NAS (полный shell).»
2. Пользователь шлёт текст / файл / голосовое — как Use (скачать вложения, собрать промпт + блок `TELEGRAM_FILES`).
3. Бот **не запускает** агента. Показывает короткое превью (первые ~400 символов текста, список имён файлов) и кнопки:
   - `Выполнить` (`cmd:cursor.nas.yes`)
   - `Отмена` (`menu:cursor`)
4. **Выполнить** → «Запускаю на NAS…» → хостовый воркер гоняет `agent` → в чат текст и файлы из блока `TELEGRAM_FILES` (чтение с диска хоста, не Cloud artifacts API).
5. **Отмена**, `/start` или любая другая кнопка (не `Выполнить`) сбрасывают ожидание и неподтверждённый черновик.

Один NAS-job за раз. Если уже бежит — «Дождись текущего NAS-запроса». Облачный Use параллельно можно не блокировать.

## Почему CLI на хосте, не в контейнере

Тот же приём, что restart/FTP: контейнер пишет задание, хост исполняет.

- CLI: `~/.local/bin/agent` (install: `curl https://cursor.com/install -fsS | bash`).
- Auth: тот же `cursor.api_key` из yaml, в окружении воркера `CURSOR_API_KEY` (не в git).
- Headless: `agent -p --force --output-format text`. Без `--force` CLI в print-режиме не применяет правки; для неинтерактивного shell на NAS `--force` обязателен (`--yolo` — синоним, не используем в коде).
- `cwd`: домашний каталог пользователя воркера (тот же, от кого уже есть `sudo docker` / shell в этой сессии). Shell всё равно может уйти в любой путь.
- Сеть до Cursor API: сначала напрямую с хоста; если не открывается — прокси из `telegram.proxy` как `ALL_PROXY`/`HTTPS_PROXY` (socks5). В лог только `type://host:port`.

## Протокол бот ↔ хост

Каталог: `xtmp-docker/cursor-nas/` (уже gitignore через `xtmp-*`).

Задание `job.json` (пример полей):

- `id` — uuid
- `status` — `queued` | `running` | `finished` | `error`
- `prompt_file` — путь к тексту промпта
- `inbox/` — вложения из Telegram, в промпте абсолютные пути
- `result_file` — stdout агента
- `error_file` — stderr / сообщение
- `pid` — pid `agent`, чтобы убить по таймауту

Бот пишет `queued` + файлы, воркер атомарно берёт job, ставит `running`, запускает `agent`, по завершении `finished`/`error`. Бот поллит `status` (интервал 2 с, бюджет как у облака: порядка 20 мин), потом читает `result_file`.

Таймаут: воркер шлёт `SIGTERM`/`SIGKILL` процессу `agent`, пишет `error`.

Воркер: отдельный скрипт `scripts/cursor-nas-watch.sh --loop` + systemd `homenas-cursor-nas.service` (рядом с `homenasbot-watch`, но **не** `BindsTo` контейнера: CLI должен пережить recreate бота, пока job бежит). `install-autostart.sh` ставит юнит. Пользователь сервиса — тот же, у кого полный shell на NAS (не root в контейнере).

## Промпт и медиа

Как Use: картинки в текст как пути к файлам в `inbox/` (CLI сам читает файлы по пути). Остальное тоже файлами в `inbox/`, не обязательно inline base64.

В конец текста — существующий `MEDIA_HINT` (`===TELEGRAM_FILES===`). Для NAS в hint явно: класть выдаваемые файлы в `cwd` (или `inbox/../out/`), `path` — абсолютный или относительно cwd; `data` base64 по-прежнему как fallback.

После `finished` бот:

1. Парсит блок, вырезает его из текста в чат.
2. Читает байты с диска (`path`) через `/host` bind, если путь под корнем хоста, иначе через каталог job (воркер копирует `out/` в `xtmp-docker/cursor-nas/<id>/out`, этот путь смонтирован в контейнер rw).
3. Шлёт voice/audio/photo/… как сейчас.

`xtmp-docker` уже rw в контейнере — исходящие файлы только оттуда, не весь `/`.

## Безопасность

- Вход по-прежнему только `telegram.allowed_ids`.
- Confirm обязателен: случайный стикер после кнопки NAS не запускает агента, пока не нажато **Выполнить**.
- После confirm — полный shell пользователя воркера. Это сознательно. Ошибки промпта могут снести файлы и контейнеры.
- В логах нет текста промпта и содержимого файлов.
- Ключ только в yaml / env юнита.

## Конфиг

В `xtmp-cnf.yaml` (плейсхолдеры в `cnf.example.yaml`):

```yaml
cursor:
  api_key: "crsr_..."
  nas:
    enabled: true
    job_dir: /xtmp-docker/cursor-nas   # внутри контейнера
    timeout_sec: 1200
```

Пути хоста для systemd — через `@ROOT@` в unit, не хардкод в Python.

## Тесты и деплой

- Юнит-тесты: стейт NAS-wait / черновик / confirm / cancel; запись-чтение job.json; разбор результата и медиа с диска; не вызывать настоящий `agent`.
- Ручная проверка: `agent --version` на хосте, один `-p --force "pong"` , затем Telegram NAS → превью → Выполнить.
- После кода: пересборка образа бота + recreate контейнера; новый systemd unit; CLI ставится один раз на хост.

## Согласованность с `.develop/rules.md`

Правило «бот не даёт shell» меняется точечно: **нет кнопки bash в меню**; shell только через Cursor → NAS после confirm, исполняет хостовый `agent`, не контейнер.
